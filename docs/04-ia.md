# 04 — Information architecture

**Agent 4, UX / IA.** Binding on Phases 3–8 the way `DECISIONS.md` and `01b-truth-audit.md` are
binding on this one. Where this file and the truth audit disagree, the audit wins.

Two rules govern every choice below.

**The reviewer clock is bimodal.** There is a ~10-second homepage verdict gate, and past it either
zero further reading or an unbounded deep read — one documented case is a Series C VP who spent
nearly an hour on a single portfolio (`02a` §4.1). There is no seven-minute reader. So the gate is
optimised ruthlessly and depth is made genuinely available, and nothing is designed for an average
that does not exist.

**Two reading orders must both work.** A generalist starts at the headline and works down. An AI-PM
reviewer opens the live URL first and searches for the eval suite second (`02a` §4.2, source-verified).
That is why Grounded gets an entry point inside the hero block and why the nav's `Lab` item does not
point at an index page.

### 2.1 Targets

| Label | Target | Why |

| *Aniket Agarwal* | `/` | Wordmark. Never resizes on scroll — a resizing wordmark is a fidget |
| Work | `/work` | Index, not case study one. A reader who clicks a nav item labelled "Work" and lands inside one project has lost the ability to see how many there are |
| Approach | `/approach` | The VP goes here first and arrives cold. The page must not assume the homepage was read |
| Lab | **`/lab/grounded`** | See §2.2 |
| About | `/about` | — |
| Resume ↗ | **`/resume`** | Not the PDF path directly. One canonical, speakable URL that survives a filename change and that Aniket can say out loud in a call |

### 2.2 Ruling: `Lab` points at `/lab/grounded`, not `/lab`

The documented AI-PM reading order is: open the live URL, search for the eval suite, read the
reflection last (`02a` §4.2, `[V — shipset.app]`). D1-29 requires a first-class entry point above
the attention cliff. A one-item index page between that reviewer and the only runnable thing on the
site is a click tax charged to exactly the reader it was built for.

So the nav item labelled `Lab` resolves to `/lab/grounded`. The Grounded page carries a breadcrumb
`Lab / Grounded` whose first crumb goes to `/lab`, so the parent is never orphaned.

**Trigger to revisit:** the day `/lab` holds two or more projects, the nav target flips to `/lab`.
Write that condition into the code comment so the next person does not have to rediscover it.

### 2.3 Condense-on-scroll, with zero client JavaScript

The nav is already built as a Server Component with a native `<details>` mobile panel. The condense
must not break that. It is a CSS scroll-driven animation and a registered custom property, and it
needs no sentinel element.

```css
/* --nav-h must be registered, or it cannot interpolate. Inherits, so the
   fixed mobile panel below picks up the animated value for free. */
@property --nav-h {
  syntax: '<length>';
  inherits: true;
  initial-value: 3.5rem;
}

.site-nav {
  --nav-h: 3.5rem;
  height: var(--nav-h);
  display: flex;
  align-items: stretch;
}

/* Every interactive item fills the bar, so the hit area is the bar height at
   both ends of the animation: 56px roomy, 44px condensed. 44px is the floor
   and the reason the condensed height is 2.75rem and not less. */
.site-nav a,
.site-nav summary {
  display: inline-flex;
  align-items: center;
  height: 100%;
}

@supports (animation-timeline: scroll()) {
  @media (prefers-reduced-motion: no-preference) {
    .site-nav {
      animation: nav-condense linear both;
      animation-timeline: scroll(root block);
      animation-range: 0 120px;
    }
  }
}

@keyframes nav-condense {
  from { --nav-h: 3.5rem;  border-bottom-color: var(--color-rule); }
  to   { --nav-h: 2.75rem; border-bottom-color: var(--color-rule-strong); }
}
```

**What animates:** bar height and the bottom rule's colour. Nothing else.

**What must not animate:** the wordmark size, `backdrop-filter` (expensive, and blur-on-scroll is a
2024 template signature), the background opacity, and any nav item's type size. `02b` line 685 is
explicit on the first and the third.

**Fallback behaviour.** With no `animation-timeline` support the `@supports` block never applies and
the nav simply stays at 3.5rem forever. That is a completely acceptable site. There is no JS fallback
and there must not be one — a scroll listener on this site would be the only client-side scroll
handler in the bundle, added for a 12px height change.

**Reduced motion.** The animation is scroll-linked, not timed, but it is still a size change the
reader did not ask for. Under `prefers-reduced-motion: reduce` the animation is not applied and the
bar stays roomy. Zero risk, zero code.

**Delete the sentinel.** `Nav.tsx` currently renders `<div className="nav-sentinel … h-30 …" />` with
a comment claiming it is 120px tall. With `--spacing: 0.5rem` in the theme block, `h-30` computes to
**240px**, not 120px — so the sentinel is already twice its documented size. `scroll(root block)` with
an explicit `animation-range: 0 120px` expresses the same intent in one line, cannot drift from its
comment, and removes a DOM node. Remove the sentinel and the `.nav-sentinel` class.

### 2.4 The mobile panel

The control is the word **Menu**, becoming **Close** when open. No hamburger, no glyph, no animated
three-line-to-X transform. Already built correctly.

Three things the built component still needs:

**(a) Scroll lock, with no JavaScript.**

```css
body:has(.nav-panel[open]) { overflow: hidden; }
```

**(b) The panel links must be plain `<a>`, not `<Link>`.** This is the one real defect in the current
implementation. Next's App Router does a soft navigation and preserves the layout, which means the
`<details>` element stays `open` — the reader taps a link and the full-screen menu remains on top of
the page they just navigated to. There is no zero-JS way to close a native `<details>` on a soft
navigation. A plain `<a>` forces a document navigation, which destroys and re-creates the panel in
its default closed state.

The cost is prefetch on four links, on a statically generated site whose lead case study is about
cold start. That is an acceptable trade and arguably the right one. Desktop nav links keep `<Link>`.

**(c) The resume link's screen-reader text must match its behaviour.** The component currently
announces "(PDF, opens in this tab)". Change the behaviour, not the text: the resume opens in a **new
tab** (`target="_blank" rel="noopener"`) and announces "(PDF, opens in a new tab)". Rationale — the
Head of Product opens the resume mid-read to check the title against the site; replacing the tab
costs them the reading position and a back-navigation. The recruiter, for whom the PDF is the
destination, loses nothing.

### 2.5 Footer

One row, mono, small: email · LinkedIn · Resume · GitHub. Nothing else. No Lighthouse badge (D1-35),
no "built with", no social icons, no back-to-top.

`site.github` is currently populated with `https://github.com/Aniket4501`, which CG B16 records as
unconfirmed — it is a local `gh` credential, not a stated public handle. **The GitHub link does not
ship until B16 is answered.** It is already correctly absent from the JSON-LD `sameAs`; the footer
must match.

## 3. Four annotated journeys

### 3.1 The recruiter — 20 seconds, phone, 390×844

Extracting eight facts in twenty seconds means roughly two and a half seconds a fact, on a 390px
screen, with no scrolling for the first six. Everything below is an ordering constraint, not a
design suggestion.

**What they see, in order:**

1. **Nav bar.** `Aniket Agarwal` and a bordered `Resume ↗`. *Fact 7 acquired in under a second,* and
   it stays acquired — the nav is sticky, so the resume is reachable at every scroll position on
   every page. This is why Resume is a button and not a nav link.
2. **H1, two lines, exact words:**
   *"The roadmap was engagement. The app took fifteen seconds to open."*
   *"I spent eight weeks there instead. We shipped it under two."*
   A recruiter is not scanning for this, but it is unavoidable and it costs about four seconds. It
   buys the two things the eight facts cannot: that he reprioritised, and that he can write.
3. **The identity block** — the densest four lines on the site, and the only place five of the eight
   facts exist together:

   ```
   Product Analyst · HCL Healthcare · Noida, India · October 2024 — present
   Roadmap and engagement features on a consumer health app with 1M+ registered
   beneficiaries.
   Open to PM and APM roles — consumer product, health, applied AI.
   ```

   *Facts 1, 2, 3, 4, 5, 6.*
4. **The link row**, immediately under it: `Resume (PDF) · LinkedIn · aniketagarwalmhq24@gmail.com`.
   *Fact 8,* and a second acquisition of fact 7. The email is plain text you can select, not a
   contact form and not a mailto-only button.
5. **The Grounded pointer**, one line, at the bottom of the hero block. Not for this reader. It is
   here for §3.4 and it must not push the link row below the fold.

**Fold budget at 390×844.** Usable height after browser chrome is ~730px. Nav 56 · H1 ≤ 420 ·
identity block ≤ 96 · link row ≤ 44 · spacing ~110. The Grounded pointer sits below the fold by
design and is the first thing revealed by a single thumb-scroll. **If the link row falls below the
fold at 390×844, the hero is over budget and the H1 leading must come down — not the identity block.**

**The eight facts, mapped:**

| # | Fact | Where it is extracted | Redundant copy |
|---|---|---|---|
| 1 | Current role | Identity line — `Product Analyst`, literal, per D1-20 | `/about`, timeline, JSON-LD |
| 2 | Years | `October 2024 — present`. **No total-years figure anywhere** (D1-05) | Timeline rows from 2022 |
| 3 | Domain | `consumer health app` | Every case-study card |
| 4 | Product scope | `Roadmap and engagement features … 1M+ registered beneficiaries` | Case-study ownership blocks |
| 5 | Location | `Noida, India` | Footer, JSON-LD `address` |
| 6 | Target role | `Open to PM and APM roles — consumer product, health, applied AI` | `/about` |
| 7 | Resume link | Nav button (persistent) + hero link row | Footer |
| 8 | LinkedIn link | Hero link row | Footer |

**The cost of fact 2, stated plainly.** A recruiter scanning for "2+ years" on a phone gets a date
range and has to do the arithmetic. That is deliberate: 22 months is not two years, the resume header
says "1.5+ Years", and a site that inflates past the candidate's own document in the inflating
direction loses more than it gains (D1-05). The mitigation is the timeline, which runs from 2022 and
reads as *in product since 2022* without making a single claim. Do not "help" the recruiter here.

**Must have understood on leaving:** who he is, where, what he owns, at what scale, what he wants,
and how to reach him — with two live links in hand.

### 3.2 The startup CEO — 90 seconds, phone

This reader is asking one question: *can this person operate without me?* They will not read a case
study. They will remember at most one thing, and the entire job of the homepage is to choose which
thing that is.

**What they see, in order:**

1. **The H1.** Ninety seconds is enough to actually read it, and it answers their question in
   nineteen words: he owned the roadmap, he found something worse than what was on it, and he moved.
2. **The identity block.** Four seconds. Scale check.
3. **The proof strip** — three cells, §5.2. They read the first: `15s → under 2s`.
4. **Case-study row 1**, the headline and the metric pair. They do not click.
5. **Beliefs.** They read one, maybe two. This is where a CEO decides whether the H1 was a lucky
   sentence or a habit of mind.
6. **Exit** — usually to LinkedIn, sometimes to the resume, occasionally to email.

**The one specific thing they must remember:** *fifteen seconds to open, under two in eight weeks —
and it wasn't on his roadmap.* Not the app, not the company, not the title.

**What makes it stick, structurally:** the number appears in the H1 in words (*fifteen seconds*), in
the proof strip in figures (`15s → under 2s`), and on case-study row 1 as a headline. Three
encodings, three visual registers, one screen apart. Nothing else on the homepage is repeated even
twice — repetition is the scarce resource here and it is spent entirely on this.

**Failure mode to guard against:** if the proof strip's other two cells are given equal visual
weight, the reader leaves with three half-remembered numbers instead of one. The cold-start cell is
first and it is the one the hero has already primed.

### 3.3 The Head of Product — 5 to 10 minutes, desktop

The brief's clock and the research's clock disagree, and the research is right. There is no
seven-minute reader; there is a ten-second gate and then a commitment. What "5–10 minutes" actually
describes is *the gate plus two case studies at the documented 2–3 minutes each*, with attention
exhausted by case study three (`02a` §4.1). Design the path so that a reader who quits after one
case study has still calibrated everything on the list.

**What they see, in order:**

| # | Where | Time | What it settles |
|---|---|---|---|
| 1 | Homepage H1 + identity | 0:00–0:15 | Register. Does the writing match the record? |
| 2 | Proof strip | 0:15–0:40 | **Numbers.** Every cell shows its qualifier at the same type size as the label. Three of them show an amber `[NEEDS:]` where the method is unpublished |
| 3 | Case-study rows | 0:40–1:00 | Scope. Three rows, stacked full-width, never a three-up grid |
| 4 | `/work/two-seconds` header block | 1:00–1:30 | **Ownership.** Role, team shape, timeline, and the `I did not` line |
| 5 | Two Seconds body | 1:30–4:00 | **Technical depth** and **trade-off reasoning** |
| 6 | One or two drawers | 4:00–5:30 | Whether the depth goes further than the page |
| 7 | Next-step link → `/work/steps-premier-league` | 5:30–8:00 | **Trade-off reasoning** again, on a decision with named alternatives |
| 8 | Exit, or `/about` for the timeline | 8:00+ | The register check from step 1, closed |

**How each calibration target is served, and where it fails if the reader stops early:**

- **Scope** — the identity block (step 1) and the case-study rows (step 3). Settled inside sixty
  seconds. Never depends on opening a case study.
- **Ownership** — the header block of every case study, and it is a schema-enforced requirement:
  `notOwned` is non-optional and the build fails without it. The `I did not` line is doing more work
  than the two lines above it. Bounding your own claim is what makes the unbounded claims believable,
  and it is the fastest available substitute for testimonials that do not exist yet.
- **Technical depth** — the body of Two Seconds, in the prose, not in a drawer. A latency argument
  that lives behind a disclosure has failed the reader who is calibrating exactly that.
- **Trade-off reasoning** — Two Seconds carries the cost of the reprioritisation; Steps Premier
  League carries the option evaluation. This reader needs both, which is why the next-step link at
  the foot of Two Seconds points at Steps Premier League and not at the work index.
- **Outcomes** — the proof strip and the per-case metric blocks, each with population, timeframe and
  method rendered at the same size as the label. **Never in a tooltip and never on hover.** A
  denominator you have to hover to see is a denominator you are hiding, and on a touch device it does
  not exist at all.

**The exit ramp rule.** Every one of steps 4 through 7 must leave the reader with the load-bearing
sentence of that section in bold, so a reader who scans only the bold lines gets the whole argument.
That rule is already in the content brief; it is an IA requirement here because it is what makes the
"quit after one case study" path survivable.

### 3.4 The VP Product — 3 minutes, then possibly 30

This reader goes to `/approach` first, often from the nav on arrival, sometimes directly from a
shared link. They are reading for judgment under ambiguity, and they have decided in three minutes
whether there is a mind here worth thirty.

**Consequence for `/approach`, and it is the whole design of the page:**

**The page assumes nothing.** No "as I described on the homepage", no pronoun whose referent is on
another route, no belief that only parses if you have read Two Seconds. Every belief states its own
evidence inline and links to the case study rather than depending on it.

**Three minutes means the page is readable in three minutes.** Three beliefs, not four (D1-37 — do
not auto-fill a fourth), one postmortem, one next step. Roughly 500–700 words of visible prose.
**`/approach` contains zero drawers** — see §5.6. A page whose job is to be read in one pass must not
ask the reader to open anything.

**What they see, in order:**

1. A one-line page statement — what this page is, and that it is opinion rather than record.
2. Belief 1, bolded claim first, two or three sentences of argument, then the link to the case study
   that evidences it.
3. Beliefs 2 and 3, same shape, different lengths. Not a three-item parallel structure — if all three
   run to the same length the page reads as generated.
4. **The postmortem.** The single visible "what I got wrong" on the entire site, rendered as an
   amber `[NEEDS:]` until Aniket answers CG B1. This is the one place the site's biggest hole is
   visible without opening anything, and its placement here rather than in three case studies is a
   deliberate ruling (D1-27): four confessions read as a format, one reads as honesty.
5. Next step → `/work/two-seconds`.

**The thirty-minute continuation.** A VP who commits goes from `/approach` into the case studies in
order and then into `/lab/grounded`. They will open drawers, and the drawers are what the thirty
minutes are spent on. This is why the disclosure content must be genuinely load-bearing argument and
not padding: the reader who opens a drawer has already decided to be convinced, and finding
restatement there is the cheapest possible way to lose them.

## 5. Progressive disclosure map

### 5.0 The rules that govern every drawer

1. **Nothing load-bearing is ever collapsed.** The decision, the trade-off, the numbers and the
   limits are visible. What collapses is the derivation, the option analysis, the metric definition
   and the method.
2. **The label is a specific claim, never "Read more".** The label must do work for the reader who
   never opens it — it advertises that the argument happened. Schema already enforces a 12-character
   minimum; that is a floor, not a target.
3. **Under ~60 words is not a disclosure, it is a parenthesis.** Inline it.
4. **All drawer content is server-rendered inside `<details>`.** It is in the HTML, hidden with CSS,
   therefore indexed and `Cmd-F`-findable while collapsed (Chrome auto-expands `<details>` on find).
   Do not build a custom disclosure. Do not inject content on click.
5. **Maximum four per case study.** Currently every case study ships three or fewer. The fourth slot
   is reserved for content that only arrives with a `CONTENT_GAPS` answer.
6. **At most one amber `[NEEDS:]` per `MetricDelta`.** Where two or more qualifying fields are
   unknown, the content file collapses the question into a single token in the `method` field and
   sets the other unknown fields to the muted literal `not stated`. Three unqualified fields
   rendering as three separate amber chips under one number reads as a broken template; one chip
   naming all three reads as someone who knows exactly what is missing from his own number.
