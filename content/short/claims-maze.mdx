A claims flow is not a growth funnel and should not be designed like one.
Nobody browses it. Everyone inside it has already had the bad thing happen and
is now doing paperwork about it, which changes what a badly placed field costs:
friction applied to an obligation nobody asked for, at the worst moment anybody
could apply it.

So the work started with the journey rather than the screens. I mapped it, found
where people stopped, and the redesign that followed went to Tech as user
stories — a form engineers can argue with, rather than a document about how the
flow ought to feel.

Drop-offs came down.

**The dashboard is the part of this that outlived me.** Real-time, tracking 50K+
user journeys, feeding sprint prioritisation. A drop-off found in a one-off
analysis is found once, by the person doing the analysis, and it goes stale the
week after. A drop-off visible in a live view of 50K+ journeys is found every
sprint by whoever happens to be looking, which is a different kind of asset —
the analysis is an answer, and the dashboard is a habit.

There is a satisfaction number attached to this work on my resume. It has no
scale, no baseline and no sample size that I can state, so I have left it off
this page rather than ask you to take it on trust.

The honest limit on all of it: three months is enough time to map a journey,
redesign it and hand over the stories. It is not enough to watch whether the
redesign held once real volume ran through it, and a claims flow is exactly the
kind of surface where the second quarter tells you more than the first.
